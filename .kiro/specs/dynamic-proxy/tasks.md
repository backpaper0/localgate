# Implementation Plan

- [x] 1. プロジェクト基盤セットアップ
- [x] 1.1 Go モジュールと CLI エントリポイントの初期化
  - Go モジュール（`go.mod`）を初期化し、cobra を依存関係として追加する
  - `localgate` コマンドのルートコマンドと `start` サブコマンドの骨格を実装する
  - `--port` フラグ（デフォルト 9000、範囲 1〜65535）のバリデーションを実装する
  - コマンド実行時に ProxyServer を初期化・起動する処理を配置する
  - SIGINT/SIGTERM を受信してグレースフルシャットダウンを行う仕組みを組み込む
  - _Requirements: 1.2, 8.1, 8.2_

- [x] 2. サービスレジストリの実装
- [x] 2.1 インメモリルーティングテーブルの構築
  - サブドメイン名をキー、バックエンドアドレスを値とするインメモリマップを実装する
  - 読み取りを並行実行できるよう `sync.RWMutex` による排他制御を組み込む
  - サービスの登録（上書き更新含む）、解除、参照、一覧取得の各操作を実装する
  - `name` および `target` の空文字チェックを実施し、無効な入力を拒否する
  - _Requirements: 3.1, 3.4, 4.1, 5.1, 5.2, 7.1, 7.2_

- [x] 2.2 サービスレジストリの単体テスト
  - 登録後に参照で正しいターゲットが返ることを検証する
  - 同名の再登録で上書きされることを確認する
  - 解除後に参照で「未登録」が返ることを検証する
  - 複数ゴルーチンから同時に読み書きしてもデータ競合が発生しないことを確認する（`go test -race`）
  - _Requirements: 3.1, 3.4, 4.1, 4.3, 7.1, 7.2_

- [x] 3. 管理 API ハンドラの実装
- [x] 3.1 (P) サービス登録エンドポイントの実装
  - `POST /services` のHTTPハンドラを実装する
  - リクエストボディを JSON でパースし、`name` と `target` の必須バリデーションを行う
  - バリデーション通過後にサービスレジストリへ登録し、201 レスポンスを返す
  - JSON パース失敗または必須フィールド不足の場合は 400 を返す
  - _Requirements: 3.1, 3.2, 3.3_

- [x] 3.2 (P) サービス解除エンドポイントの実装
  - `DELETE /services/{name}` のHTTPハンドラを実装する
  - パスパラメータから削除対象の名前を取得し、サービスレジストリから削除する
  - 正常削除時は 204 を返し、指定名が未登録の場合は 404 を返す
  - _Requirements: 4.1, 4.2, 4.3_

- [x] 3.3 (P) サービス一覧エンドポイントの実装
  - `GET /services` のHTTPハンドラを実装する
  - サービスレジストリから全エントリを取得し、JSON 配列として 200 レスポンスを返す
  - 登録がない場合は空の配列を返す
  - _Requirements: 5.1, 5.2_

- [x] 4. リバースプロキシ転送の実装
- [x] 4.1 (P) サブドメイン抽出ロジックの実装
  - Host ヘッダからポート番号を除去したうえでドット区切りでパースし、サブドメイン部分を抽出する
  - `foo.localhost` → `"foo"`、`localhost` → `""` となるロジックを実装する
  - ホスト名が空または不正な形式の場合は空文字を返す
  - 抽出ロジックの単体テストを作成し、代表的な入力パターンを網羅する
  - _Requirements: 2.1_

- [x] 4.2 (P) httputil.ReverseProxy を用いたバックエンド転送の実装
  - ターゲットアドレスに対して `httputil.ReverseProxy` を構築し、リクエストを転送する
  - HTTPメソッド、ヘッダ、ボディを保持してバックエンドへ送信する
  - バックエンドへの接続が失敗した場合は 502 Bad Gateway をクライアントへ返す
  - _Requirements: 2.2, 2.3, 2.4, 2.5, 2.6_

- [x] 5. プロキシサーバの統合実装
- [x] 5.1 HTTPサーバ起動とルーティング判定の実装
  - 指定ポートで `http.Server` を起動する処理を実装する
  - 受信リクエストの Host ヘッダからサブドメインを抽出し、サブドメインがあればプロキシハンドラへ、なければ管理 API ハンドラへ振り分ける
  - サービスレジストリでターゲットを検索し、登録済みであれば転送先を決定する
  - _Requirements: 1.1, 1.3, 2.1, 2.2_

- [x] 5.2 エラー処理の実装
  - サブドメインに対応するサービスが未登録の場合に 404 Not Found を返す
  - Host ヘッダが存在しない、または不正なフォーマットの場合に 400 Bad Request を返す
  - 各エラーレスポンスは JSON 形式で `{"error": "..."}` を含む
  - _Requirements: 6.1, 6.2_

- [x] 6. 統合テストの実装
- [x] 6.1 エンドツーエンドのプロキシ動作テスト
  - テスト用バックエンドHTTPサーバを起動し、サービス登録後に `foo.localhost` へのリクエストが正しく転送されることを確認する
  - 登録削除後に同一サブドメインへのリクエストが 404 を返すことを確認する
  - 未登録のサブドメインへのアクセスが 404 を返すことを確認する
  - バックエンドダウン時に 502 が返ることを確認する
  - _Requirements: 2.2, 2.6, 6.1, 7.1, 7.2_

- [x] 6.2 管理 API の統合テスト
  - `POST /services` でサービスを登録後、`GET /services` の一覧に含まれることを確認する
  - `DELETE /services/{name}` で削除後、`GET /services` から消えることを確認する
  - 未登録名への `DELETE` が 404 を返すことを確認する
  - 必須フィールド不足の `POST` が 400 を返すことを確認する
  - _Requirements: 3.2, 3.3, 4.2, 4.3, 5.1, 5.2_

# Requirements Document

## Project Description (Input)
ローカルサービスのための動的プロキシ

### 1. 概要

本システムは、HTTPリクエストをサブドメインに基づいてバックエンドサービスへ転送する **リバースプロキシ**である。
バックエンドサービスはAPI経由で動的に登録・解除できる。

主にローカル環境または内部ネットワーク上の複数サービスを、単一のHTTPエンドポイントから利用可能にすることを目的とする。

### 2. 前提条件

* 本システムはHTTPリバースプロキシとして動作する
* バックエンドサービスはHTTPで通信可能である
* クライアントはHostヘッダを用いてアクセスする
* DNSまたはhosts設定により `*.localhost` がローカルホストへ解決される

例

```
foo.localhost
bar.localhost
```

### 3. 用語

| 用語         | 説明                       |
| ---------- | ------------------------ |
| プロキシ       | 本システムのHTTPサーバ            |
| バックエンドサービス | プロキシがリクエストを転送するHTTPサービス  |
| サービス登録     | バックエンドサービスをプロキシに登録する操作   |
| ルーティング     | サブドメインに基づいてバックエンドへ転送する処理 |

### 4. 機能要件

#### 4.1 HTTPサーバ機能

1. プロキシは指定ポートでHTTPサーバとして待ち受けること
2. クライアントからのHTTPリクエストを受信できること

例

```
http://foo.localhost:9000
```

#### 4.2 サブドメインルーティング

1. プロキシはHTTPリクエストの **Hostヘッダ**を取得すること
2. Hostヘッダのサブドメイン部分を抽出すること
3. サブドメインに対応するバックエンドサービスへリクエストを転送すること

例

| Host          | 転送先            |
| ------------- | -------------- |
| foo.localhost | service_a:3000 |
| bar.localhost | service_a:8000 |
| baz.localhost | service_b:8080 |

#### 4.3 リバースプロキシ機能

プロキシは以下を実装すること

1. クライアントのHTTPリクエストをバックエンドへ転送する
2. バックエンドからのレスポンスをクライアントへ返す
3. HTTPメソッド（GET, POST 等）を保持する
4. HTTPヘッダを転送する
5. リクエストボディを転送する

#### 4.4 サービス登録API

プロキシはバックエンドサービスを **HTTP API** により登録できること。

##### 登録

HTTP POSTリクエストによりサービスを登録できること。

登録内容

| 項目     | 説明         |
| ------ | ---------- |
| name   | サブドメイン名    |
| target | バックエンドアドレス |

例

```
POST /services
```

登録例

```
foo → service_a:3000
bar → service_a:8000
```

#### 4.5 サービス解除API

登録済みサービスを削除できること。

```
DELETE /services/{name}
```

例

```
DELETE /services/foo
```

#### 4.6 サービス一覧API

現在登録されているサービスを取得できること。

```
GET /
```

または

```
GET /services
```

レスポンスには以下を含むこと

| 項目     | 説明     |
| ------ | ------ |
| name   | サブドメイン |
| target | 転送先    |

#### 4.7 未登録サービスへのアクセス

サブドメインに対応するサービスが登録されていない場合、プロキシはエラーを返すこと。

例

```
404 Not Found
```

### 5. 非機能要件

#### 5.1 動的設定

サービス登録および解除は **プロキシの再起動なしで反映されること**。

#### 5.2 軽量性

プロキシは単一プロセスで動作可能であること。

#### 5.4 起動方法

プロキシは単一コマンドで起動可能であること。

例

```
localgate start
```

### 6. 使用例

#### 6.1 サービス登録

```
foo → localhost:3000
bar → localhost:8000
baz → localhost:8080
```

#### 6.2 アクセス例

```
http://foo.localhost:9000 → localhost:3000
http://bar.localhost:9000 → localhost:8000
http://baz.localhost:9000 → localhost:8080
```

### 7. 想定ユースケース

* ローカル開発環境で複数サービスを公開
* マイクロサービス開発
* コンテナ環境でのサービスゲートウェイ
* 開発用簡易リバースプロキシ

## Requirements

### イントロダクション

LocalGate は、ローカルおよび内部ネットワーク上で動作する複数のHTTPサービスを、サブドメインベースのルーティングにより単一エンドポイントから利用可能にするリバースプロキシである。バックエンドサービスの登録・解除は再起動不要のHTTP APIで行える。

### 要件 1: HTTPサーバ起動・待ち受け

**目的:** 開発者として、指定ポートでHTTPサーバを起動したい。それにより、単一エンドポイントで複数のローカルサービスにアクセスできる。

#### 受入基準

1. The LocalGate shall 指定されたポートでHTTPサーバとして待ち受けること。
2. When `localgate start` コマンドが実行されたとき、the LocalGate shall HTTPサーバを起動すること。
3. The LocalGate shall クライアントからのHTTPリクエストを受信できること。

---

### 要件 2: サブドメインルーティング

**目的:** 開発者として、Hostヘッダのサブドメインに基づいてリクエストを適切なバックエンドへ転送したい。それにより、複数のサービスを単一ポートで識別・利用できる。

#### 受入基準

1. When HTTPリクエストを受信したとき、the LocalGate shall Hostヘッダからサブドメインを抽出すること。
2. When サブドメインが抽出されたとき、the LocalGate shall 対応する登録済みバックエンドサービスへリクエストを転送すること。
3. The LocalGate shall HTTPメソッド（GET、POST、PUT、DELETE 等）を保持してバックエンドへ転送すること。
4. The LocalGate shall HTTPリクエストヘッダをバックエンドへ転送すること。
5. The LocalGate shall HTTPリクエストボディをバックエンドへ転送すること。
6. When バックエンドからレスポンスを受信したとき、the LocalGate shall そのレスポンスをクライアントへ返すこと。

---

### 要件 3: サービス登録API

**目的:** 開発者として、HTTP APIでバックエンドサービスを登録したい。それにより、プロキシを再起動せずに動的にサービスを追加できる。

#### 受入基準

1. When `POST /services` リクエストを受信したとき、the LocalGate shall `name`（サブドメイン）と `target`（バックエンドアドレス）を受け取りサービスを登録すること。
2. When サービスが正常に登録されたとき、the LocalGate shall 成功レスポンスを返すこと。
3. If 必須フィールド（`name` または `target`）が欠けているとき、the LocalGate shall エラーレスポンスを返すこと。
4. When 同一の `name` でサービスを再登録したとき、the LocalGate shall 既存のエントリを上書き更新すること。

---

### 要件 4: サービス解除API

**目的:** 開発者として、HTTP APIで登録済みサービスを削除したい。それにより、不要になったサービスをプロキシの再起動なしに除外できる。

#### 受入基準

1. When `DELETE /services/{name}` リクエストを受信したとき、the LocalGate shall 指定された名前のサービスをルーティングテーブルから削除すること。
2. When サービスが正常に削除されたとき、the LocalGate shall 成功レスポンスを返すこと。
3. If 指定された `name` が登録されていないとき、the LocalGate shall 404エラーレスポンスを返すこと。

---

### 要件 5: サービス一覧API

**目的:** 開発者として、現在登録されているサービス一覧を取得したい。それにより、プロキシの状態を確認できる。

#### 受入基準

1. When `GET /services` リクエストを受信したとき、the LocalGate shall 登録済みサービスの一覧（`name` と `target` を含む）を返すこと。
2. When サービスが1件も登録されていないとき、the LocalGate shall 空の一覧を返すこと。

---

### 要件 6: 未登録サービスへのエラー処理

**目的:** 開発者として、未登録のサブドメインへのアクセスに対して明確なエラーを受け取りたい。それにより、誤設定をすぐに把握できる。

#### 受入基準

1. If リクエストのサブドメインに対応するサービスが登録されていないとき、the LocalGate shall HTTP 404 Not Found レスポンスを返すこと。
2. If Hostヘッダが存在しない、またはサブドメインを含まないとき、the LocalGate shall エラーレスポンスを返すこと。

---

### 要件 7: 動的設定（再起動不要）

**目的:** 開発者として、サービスの登録・解除をプロキシの再起動なしに反映したい。それにより、開発中のサービス追加・削除がシームレスに行える。

#### 受入基準

1. While プロキシが稼働中のとき、the LocalGate shall サービス登録APIで追加されたサービスを即座にルーティングテーブルに反映すること。
2. While プロキシが稼働中のとき、the LocalGate shall サービス解除APIで削除されたサービスを即座にルーティングテーブルから除外すること。

---

### 要件 8: 単一コマンド起動

**目的:** 開発者として、単一コマンドでプロキシを起動したい。それにより、セットアップの手間を最小化できる。

#### 受入基準

1. When `localgate start` コマンドを実行したとき、the LocalGate shall HTTPサーバを起動しリクエストの受付を開始すること。
2. The LocalGate shall 単一プロセスとして動作すること。
